# L2 决策记录写作细则

> 格式骨架见 `docs/decisions/_template.md`（复制后填写）；索引格式见 `docs/decisions/README.md`。
> 本文件写"何时建条、每节怎么写、修订怎么选路"的判断细则。
> 出处：`docs/design/governance-retrospective.md` 反模式 #1/#4/#5 及 ashare-lake 实战沉淀（54 条决策的失范样本）。

## 何时建条

- **建**：影响项目方向的架构、技术选型、核心接口修改——判据：下个会话的 Agent 看了代码会问"为什么不用 X"，就值得一条。
- **不建**：纯实现细节（代码可自解释）、bug 修复、模板占位符文字微调、无方向影响的常规功能实现。
- 时点：**立即建**，随代码同一次提交；"补记"会导致理由失真（记忆里的理由是重构过的）。
- AGENTS.md §4 的 Ask-first 事项只在决策记录里作出处引用（「Ask-first 见 AGENTS.md §4」），不复制清单——反模式 #5 的改法。

## 每节怎么写（对照 _template.md）

- **决策内容**：一句话，写"决定了什么"，不写论证。
- **选择理由**：至少覆盖三问——解决了什么问题？相比现状的收益？受什么约束（性能/兼容性/熟悉度）？
- **被否决的替代方案**：表格逐条列，否决原因必须具体到技术事实（忌「不好」「不优雅」「不够好」这类空泛表述）；评估类记录（spike/选型）可并入选择理由不单列表。
- **影响范围**：涉及文件、兼容性影响（迁移/破坏性变更）、**后续约束**——后续约束是新会话修改相关模块时的强制条款，写具体行为（「新增端点必须过 datasource 层」），不写「注意性能」。

## 修订双路径（选路判据）

| 变更性质 | 路径 | 动作 |
| --- | --- | --- |
| 小补充 / 实况追记 | 追记 | 文末追加 `### 追记 YYYY-MM-DD` 节 + 同步状态行；写明性质（「流程小修，非方向推翻」） |
| 方向性推翻 | 另建新条 | 不覆盖旧记录；新旧互相引用；旧条状态行改「已被 <新决策文件名> 取代」 |
| 部分取代 | 混合 | 旧条状态行只写「部分条款已被 <文件> 取代」，明细归新条 |

- 信号：同一主题追记超过 3 次 → 该"另建新条"了（反模式 #4 实测：19/54 含失范追记）。
- 被取代的决策**必须真的标状态行**——留档条目的结论以取代者为准，不标状态 = 新会话读到过时结论。

## 索引维护（decisions/README.md）

- 创建条目时**同步**追加一行：日期｜标题（链接）｜状态｜一句话（可选）。建条不登索引 = 决策可存不可查。
- 一句话摘要是给"新会话起步只读最近 3 条"准备的——值得写好，一句说清这条决策管什么。
- 按日期序在文末追加，不重排；被取代条目保留留档，不删除。

## 病态自查清单

- [ ] 建条了但索引没同步？
- [ ] 否决原因写成了「不好」？
- [ ] 后续约束写成了不可判定的「注意 XX」？
- [ ] 追记没有日期节、直接改正文？
- [ ] 被取代的条目状态行没标？
- [ ] Ask-first 事项被复制进了决策记录（应只作出处引用）？
