# L1 维护细则（AGENTS.md 与模板规则）

> 本文件管"规则怎么改才合规"。复盘流程见 `governance-review.md`。

## 收录铁律判定（写入前逐行过）

- 每一行问："删掉它，Agent 会犯错吗？"——不会，就删。
- Agent 读代码、构建文件、`--help` 即可获知的信息不入 L1；参数级细节给指针不展开。
- 可判定性：每条规则必须能被 lint、测试或评审验证；「注意代码质量」这类不可执行表述禁止出现。
- 单行 ≤200 字符；行数逼近预算时先触发修剪而非压缩措辞。

## 写入前查重

- 新规则先搜全仓（AGENTS.md、docs/）确认无第二份表述；他处已有的只作出处引用，不复制。
- 新规则写入唯一对应章节：命令类 → §2，风格红线 → §3，安全与 Ask-first → §4，记忆协议 → §5，文档同步 → §6；Ask-first 新事项一律进 §4 集中清单。
- 项目级特例放子目录 AGENTS.md（离被改文件最近的优先），不膨胀根文件。

## 修订流程（单条规则变更）

1. 确认变更性质：小补充 → 决策记录文末追记；方向性推翻 → 另建新决策记录并互相引用，旧条状态行改「已被 <新决策> 取代」（选路判据见 vibe-memory 的 decision-writing 细则）。
2. 先落决策记录，再改规则文件——顺序不可反，防止"改了没留痕"。
3. 修改 `skills/vibe-init/assets/`（模板唯一正本）或项目本地 AGENTS.md；改模板的同步刷新 `docs/design/` 对应文档的变更日期与原因标注。
4. 验证：模板改动复跑 vibe-init 脚手架（临时目录双跑）+ 打包校验，展示输出。

## 优先级冲突裁决

裁决链：**人类明确指令 > 离被改文件最近的 AGENTS.md > 仓库根 AGENTS.md > 代码现状**。

- 冲突出现时当场裁决并说明依据的链级；裁决结论固化进对应层的规则文件，不得留在对话里（对话会丢，规则不丢）。
- 相抵的规则对（文本规则 vs 实测衍生规则）按复盘流程调和：终态语义保留，写法取实测可行的那个，明文写入 L1（反模式 #3 的裁决先例）。

## 修剪

- 定期自查："Agent 读代码即可获知"的冗余是 L1 膨胀的主因，发现即删。
- L1 预算（≤100 行且单行 ≤200 字符）超标 = 复盘信号，转 `governance-review.md` 流程处理，不就地硬压。
