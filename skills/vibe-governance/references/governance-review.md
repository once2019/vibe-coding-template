# 治理复盘细则

> 方法论正本：项目内 `docs/design/governance-retrospective.md`（历史证据、8 反模式原文、8 问自查清单）。
> 本文件只写"怎么执行一轮复盘"的操作流程；清单型内容读正本，不在此复制。

## 复盘流程（五步）

1. **收集症状**（只认运行痕迹）：
   - 读项目内 `docs/design/governance-retrospective.md` 的「存量项目自查（8 问）」节，逐问实测作答；
   - 实测手段：记忆文件行数与最长行实测（对照双预算）、决策索引行数与最近 3 条质量、同主题决策追记计数（grep「追记」）、疑似分叉规则的全文对比、近期会话收尾三件套留痕抽查。
2. **列清单**：每条症状按「问题 → 证据 → 改法」格式登记；无证据的体感不入清单（"感觉 Agent 总忘事"不是证据，"handoff 缺失 3 次"是）。
3. **逐条裁决**：每条独立裁决为 采纳 / 否决 / 改写，写明理由；相抵的规则对（文本规则 vs 实测写法）在此调和——终态语义保留，写法取实测可行的那个。
4. **统一修订**：裁决完的改法直接修改模板/规则文件，每处标注变更日期与原因；改模板走 `l1-maintenance.md` 修订流程（先决策记录后改文件）。
5. **治理收口**：决策记录与索引同步（写作细则见 vibe-memory）；docs 与代码同一次提交；展示验证输出（脚手架回归 + 打包校验）。

## 产出物格式

- 固定为「问题→证据→改法」表格，列：`# / 反模式 / 实测证据 / 改法（已进模板何处）`。
- 复盘全文（含背景与证据）存 `docs/design/governance-retrospective.md` 或新增 `docs/design/` 下的复盘文档，头部标注变更日期与原因；改法已固化的部分更新进模板本体，复盘文档保留证据链。
- 复盘文档末尾刷新「什么时候该再复盘」的信号清单（与 SKILL.md 的 5 信号保持一致，若本轮修订了信号定义）。

## 原则

- 反模式不可怕，可怕的是只有体感没有证据、只有清单没有裁决。
- 复盘是治理体系唯一的自我修正通道：发现规则被反复违反，先修规则再按新规则执行，不允许"下不为例"。
- 8 问自查与 5 信号的正本在 `docs/design/governance-retrospective.md`；若复盘结论修改了信号定义，两处同步（SKILL.md 触发词一并更新）。
